# Cric Journal

A live cricket scores platform: live scores, ball-by-ball commentary, full scorecards, series and points tables, teams, player career stats, rankings and news. It ships with:

- **A mobile-first web app** that you can install as a PWA (home-screen icon, standalone window, offline cache, bottom navigation on phones, dark mode).
- **A REST API** described with OpenAPI 3.1, plus **Server-Sent Event streams** for live ball-by-ball updates.
- **An MCP server** (Model Context Protocol) so AI assistants and agents can query matches, scorecards, players and more. It works over Streamable HTTP and over stdio.

> All teams use real country names, but **every player, match and result is simulated demo data** generated by the built-in ball-by-ball engine. Wire in a real data feed to go live (see [Scaling](#scaling--going-to-production)).

## Quick start

```bash
npm install
npm run dev            # http://localhost:3000 (auto-reload)
```

Production build:

```bash
npm run build && npm start
```

Docker (portable, with data persisted to a volume):

```bash
docker compose up --build
```

| URL | What |
| --- | --- |
| `http://localhost:3000/` | Web app / PWA |
| `http://localhost:3000/docs` | API and MCP developer docs |
| `http://localhost:3000/api/v1` | REST API |
| `http://localhost:3000/api/openapi.json` | OpenAPI spec |
| `http://localhost:3000/mcp` | MCP endpoint (Streamable HTTP) |

Three matches are live when the server starts. The engine bowls one delivery every `LIVE_TICK_MS` milliseconds (4 s by default). When a match finishes, the next fixture in that series is brought forward, so there is always something live.

## Mobile

The UI is designed for phones first (360–430 px) and scales up to a two-column desktop layout.

- **On your phone:** run the server and open `http://<your-computer-LAN-IP>:3000` on the same Wi-Fi. Then use *Add to Home Screen* (iOS Safari) or *Install app* (Android Chrome).
- **In the browser:** use Chrome DevTools device mode on `http://localhost:3000`.
- **Automated:** `npm run test:e2e` runs Playwright against localhost, emulating an iPhone 13, a Pixel 7 and a desktop. It visits every page and checks that:
  - the content renders
  - there is no horizontal scrolling
  - the bottom navigation works
  - the PWA manifest and service worker are in place
  - live commentary updates over SSE
  - the app works offline
  - there are no console errors

  Screenshots are saved to `screenshots/`.

```bash
npm run build && LIVE_TICK_MS=1500 npm start &
BASE_URL=http://localhost:3000 npm run test:e2e
```

- **Native apps:** the PWA can be wrapped as an iOS or Android app with Capacitor or a Trusted Web Activity. A native app can also call the REST API and SSE streams directly. CORS is configurable with `CORS_ORIGINS`.

## REST API

```bash
curl localhost:3000/api/v1/matches?status=live
curl localhost:3000/api/v1/matches/{matchId}              # live state: batters, bowler, CRR/RRR, recent overs
curl localhost:3000/api/v1/matches/{matchId}/scorecard
curl localhost:3000/api/v1/matches/{matchId}/commentary?limit=20
curl -N localhost:3000/api/v1/matches/{matchId}/stream    # SSE: toss, ball, innings_end, match_end
```

Other endpoints are `/series`, `/series/{id}` (fixtures and points table with NRR), `/teams/{id}`, `/players?q=`, `/players/{id}` (career stats by format), `/rankings?format=&category=`, `/news` and `/search?q=`. The full list is at `/docs` and `/api/openapi.json`.

- Validation errors return `400`, unknown resources return `404`.
- Responses carry `RateLimit-*` headers. Sending an `x-api-key` from `API_KEYS` raises the limit tenfold.

## MCP for AI agents

The server offers:

- **Tools:** `list_matches`, `get_match`, `get_scorecard`, `get_commentary`, `get_squads`, `list_series`, `get_series`, `list_teams`, `get_team`, `find_players`, `get_player`, `get_rankings`, `list_news`, `search`. All are read-only.
- **Resources:** `cricket://matches/live` and `cricket://matches/{matchId}`.
- **Prompt:** `match_summary`.

Over HTTP, for Claude Code or any client that supports Streamable HTTP:

```bash
claude mcp add --transport http cric-journal http://localhost:3000/mcp
```

Over stdio, for desktop clients such as Claude Desktop:

```json
{ "mcpServers": { "cric-journal": { "command": "node", "args": ["/abs/path/cric_journal/dist/mcp/stdio.js"] } } }
```

Set `MCP_TOKEN` to require `Authorization: Bearer <token>` on `/mcp`.

## Architecture

```
                ┌───────────── Web/PWA (public/) ─────────────┐
                │  vanilla ES modules · History routing · SSE │
                └───────────────┬─────────────────────────────┘
   AI agents ── /mcp (MCP) ─┐   │ /api/v1 (REST + SSE)
                            ▼   ▼
                     ┌──────────────────┐     ┌──────────────┐
                     │  CricketService  │◀────│  LiveEngine  │── PubSub (hub) ──▶ SSE clients
                     │ (DTOs, stats,    │     │ (ticks live  │
                     │  points, search) │     │  matches)    │
                     └────────┬─────────┘     └──────┬───────┘
                              ▼                      ▼
                     ┌──────────────────┐   ┌──────────────────┐
                     │   Repository     │   │ MatchSimulator / │
                     │ (InMemory+JSON)  │   │ scoring (pure)   │
                     └──────────────────┘   └──────────────────┘
```

- **Event-sourced scoring.** Matches are stored as ball-by-ball logs. Totals, scorecards, maidens, fall of wickets, NRR and career stats are all derived by pure functions in `src/engine/scoring.ts`, which are unit-tested.
- **Ports and adapters.**
  - `Repository` (storage) and `PubSub` (realtime) are interfaces, so you can swap in Postgres or Redis without touching the API, MCP or UI code.
  - The REST API and MCP server are thin adapters over one `CricketService`.
- **12-factor config.** All settings come from environment variables (see `.env.example`).

```
src/
  domain/types.ts         core model (Match, Innings, Ball, Player, …)
  engine/                 scoring (pure), simulator, seeded RNG
  data/                   repository interface + in-memory/JSON store, demo seed
  services/               CricketService façade, LiveEngine
  realtime/hub.ts         pub/sub for live updates
  api/                    REST router, OpenAPI spec
  mcp/                    MCP server, HTTP + stdio transports
  app.ts, index.ts        composition root, HTTP server
public/                   PWA: index.html, app.js, styles.css, sw.js, manifest, icons, docs.html
test/                     unit + API + MCP integration tests (node:test)
scripts/                  Playwright mobile e2e, icon generation
```

## Scaling / going to production

| Concern | Today | Swap to |
| --- | --- | --- |
| Data | `InMemoryRepository` (+ JSON snapshot via `DATA_FILE`) | Postgres/Mongo implementation of `Repository` |
| Live feed | `MatchSimulator` inside `LiveEngine` | Ingestion worker for an official scoring feed that emits the same `Ball` events |
| Realtime fan-out | `LocalHub` (in-process) | Redis/NATS implementation of `PubSub`, for many instances behind a load balancer |
| Rate limiting | In-memory, fixed window | Redis-backed limiter or API gateway |
| MCP | Stateless Streamable HTTP | Already horizontally scalable (no sticky sessions) |

The HTTP layer is stateless apart from SSE connections, so you can run as many replicas as you need once storage and pub/sub are external.
